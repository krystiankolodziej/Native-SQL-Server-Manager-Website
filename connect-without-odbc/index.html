Connecting to SQL Server from a Mac without ODBC drivers

ODBC is not the protocol SQL Server speaks. It is a layer people install because their client insists on it — and on macOS that layer is where the afternoon goes.

What the usual setup actually involves

Follow almost any guide to reaching SQL Server from a Mac and you end up assembling four separate things:

  • A driver manager — normally unixODBC, installed through Homebrew.
  • Microsoft’s ODBC driver for SQL Server, from a separate tap.
  • A TLS library the driver was built against, whose version has to match.
  • Configuration files — odbcinst.ini and odbc.ini, recording absolute paths to libraries that Homebrew is free to move on the next upgrade.

When all four agree, this works well. The trouble is that they are versioned independently and updated on different schedules. A macOS upgrade, a Homebrew upgrade, or a move from Intel to Apple silicon — where the prefix itself changes from /usr/local to /opt/homebrew — can leave a configuration file pointing confidently at a library that is no longer there. The error you get back is rarely about the file that is wrong.

Add Kerberos or Entra ID to the picture and the layering gets deeper still, because the authentication has to be negotiated by the driver on your behalf, using settings you supply through a connection string in a syntax you now also have to know.

What SQL Server actually speaks

Underneath every driver is TDS — Tabular Data Stream. It is the protocol that defines how a client presents a login, how a batch of T-SQL travels to the server, and how the server sends back column metadata, rows, messages, errors and the shape of each result set. Everything else in that stack exists to translate between TDS and an API somebody preferred.

Native SQL Server Manager implements TDS itself, in Swift. There is no driver to install, no driver manager, no .ini file, no Homebrew, no Java runtime and no Electron. The app opens a socket, negotiates encryption, performs the login and reads the stream.

What that buys you beyond a shorter install

Removing the middle layer is not only about setup time. Several things the app does are only possible because it can see the protocol:

  • Cancelling a query for real. A long-running statement is cancelled by sending a TDS attention signal and draining the stream properly, rather than by dropping the connection and hoping.
  • Every message from a batch. A batch that raises several errors and prints several messages returns all of them, in order, alongside whichever result sets did come back — instead of the first error replacing everything.
  • Values exactly as the server sent them. Dates, times and offsets are rendered the way SSMS renders them, with no silent time-zone conversion in a driver you did not configure. Binary, rowversion and geography columns are left alone until you ask for hex or a preview.
  • Streaming results. Rows are read off the wire and appended to the grid’s backing store as they arrive, instead of the whole result being materialised twice — so a large result costs less memory, even though the grid itself is drawn once the batch finishes.

Sign-in without the driver in the way

Because authentication is handled by the app rather than delegated, the awkward mechanisms are ordinary options in a dialog: SQL logins, Microsoft Entra ID, Kerberos single sign-on with no password at all, and NTLM where Kerberos is unavailable. Encryption and certificate trust are visible checkboxes rather than connection-string fragments.

Questions

Do I need an ODBC driver to connect to SQL Server from a Mac?

Only if your client is built on one. ODBC is an abstraction layer, not the protocol SQL Server speaks. A client that implements TDS — the actual wire protocol — connects with nothing else installed.

What is TDS?

TDS, or Tabular Data Stream, is the protocol SQL Server speaks over the network: how a login is presented, how a batch of T-SQL is sent, and how result rows, column metadata, messages and errors come back. Every SQL Server client ends up speaking it, directly or through a driver.

Why does my ODBC setup break after a macOS or Homebrew update?

Because the working configuration spans several independently versioned pieces — the driver manager, the Microsoft driver, OpenSSL and the paths recorded in odbcinst.ini. An upgrade to any one of them can leave the others pointing at a library that is no longer where it was.
