Kerberos single sign-on to SQL Server from a Mac

Windows authentication is not a Windows-only feature. macOS has carried a complete Kerberos implementation for two decades, and SQL Server is happy to accept a ticket from it. What is usually missing is a client that can present one.

What Windows authentication really is

“Windows authentication” names two different mechanisms that SQL Server treats as one option in a dialog box. The modern one is Kerberos: your machine obtains a ticket from the domain controller, hands a service ticket to SQL Server, and the server reads your identity out of it. The older one is NTLM, a challenge–response exchange that proves you know a password without sending it.

Neither of them requires Windows on the client side. Kerberos is an open standard, and macOS implements it in the operating system — the same machinery behind kinit and klist in Terminal. The obstacle on a Mac has never been the protocol. It has been that most SQL clients reach SQL Server through an ODBC driver, and getting that driver to negotiate Kerberos correctly is an afternoon most people would rather not spend.

Getting a ticket

Kerberos starts with a ticket-granting ticket. If your Mac is bound to the domain, or you sign in through an identity agent your organisation manages, you already have one. If not, ask for one: 

kinit your.name@CORP.EXAMPLE.COM
klist

Two details cost people more time than anything else here:

  • The realm is not always the DNS domain. A company whose servers answer to ad.example.com may well run a Kerberos realm called CORP.EXAMPLE.COM. Ask, or read it out of klist once a colleague’s machine has a working ticket. Guessing wrong produces an authentication failure that looks like a password problem and is not one.
  • Case matters. Realms are conventionally uppercase and Kerberos compares them literally. corp.example.com and CORP.EXAMPLE.COM are not the same realm.

klist should now show a krbtgt/ entry with an expiry date. That ticket is the whole of what a client needs; there is nothing to type into the app.

The service principal name

Before the domain controller will issue a service ticket for your database server, it has to know that the server exists as a principal. That registration is the service principal name, and for SQL Server it looks like this: 

MSSQLSvc/sqlserver.corp.example.com:1433

The port is not decoration. A SQL Server on a non-default port needs an SPN that names that port, and an instance reached through the SQL Server Browser may have an SPN written with the instance name instead. If the SPN is missing or registered against the wrong account, Kerberos cannot proceed and the connection fails — often with “Login failed. The login is from an untrusted domain”, error 18452. Switching the picker to NTLM is then the way round it. Your domain administrator can confirm the registration with setspn -L against the SQL Server service account.

A useful sanity check before blaming authentication at all: make sure port 1433 on that host is actually reachable from your Mac. A firewall that silently drops the connection produces symptoms that are easy to mistake for a Kerberos problem.

Connecting

With a ticket in hand, connecting is the least interesting part. In Native SQL Server Manager you choose Kerberos in the connection dialog, enter the host and database, and connect. There is no user name field and no password field, because there is nothing to type: the ticket already says who you are.

When Kerberos is not an option: NTLM

Kerberos needs a domain controller you can reach and an SPN that exists. Away from the office network, or against a server nobody has registered properly, NTLM still works. It asks for your domain user name and password and performs the challenge–response exchange itself.

One wrinkle worth knowing, because it produces a login failure that looks like a typo: NTLMv2 folds the domain name into its key derivation in a specific case, so a domain typed as corp and one typed as CORP are not interchangeable everywhere in the exchange. The app normalises this for you — but if you have ever had an NTLM login rejected by SQL Server while the same credentials worked from a Windows machine, this is a likely culprit.

Why the client matters

Native SQL Server Manager implements TDS, the SQL Server wire protocol, directly. That is what makes single sign-on straightforward rather than an ordeal: there is no ODBC driver in the middle to configure, no odbc.ini, no Homebrew formula that needs reinstalling after every macOS update, and no Windows virtual machine to keep alive just so you can run a query. The app asks macOS for a service ticket and puts it on the wire.

Questions

Can a Mac use Windows authentication against SQL Server?

Yes. macOS ships with a full Kerberos implementation, and SQL Server accepts Kerberos tickets as Windows authentication. Once your Mac holds a ticket for the domain, a client that speaks TDS directly can sign in with no password prompt at all. NTLM is available where Kerberos is not.

Do I need to join the Mac to the domain for Kerberos SSO?

No. Domain binding is one way to get tickets automatically, but it is not a requirement. Running kinit with your domain account is enough to obtain a ticket-granting ticket, and that ticket is all the client needs.

Why does SQL Server reject my Kerberos login with error 18452?

Error 18452 — login from an untrusted domain — usually means the server could not tie your credential to a domain principal. The common causes are a missing or wrong service principal name on the SQL Server service account, an expired ticket, or a realm name written in the wrong case.
